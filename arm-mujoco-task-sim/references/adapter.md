# 任务适配器与项目协议

agent 根据确认后的任务，在工作区生成 `scene/scene.xml`、资产、规划文件和 `code/task.py`。本 skill 不会只靠一句文字自动推导物理参数；缺项先确认。模型和方案变化后重新规划和验证。

```python
    # 建立规划/感知/状态机并打开自己的观测证据记录。
    return Controller(...)

class Controller:
    def control(self, model, data):
        # data 在当前仿真时刻已 forward，可读取 site/body、传感器。
        # 更新 ctrl 或有明确定义的外力；不要写 qpos/qvel/time。
        # 不能在这里调用 mj_step，统一由框架执行。
        return {"cycle": 1, "phase": "approach", "done": False, "events": []}

    def evaluate(self, model, data):
        # 使用任务实际观测计算，不得直接复制请求中的轮数或写死 True。
        return {"success": False, "cycles_completed": 0, "per_cycle": []}
```

`cycle` 是 1 起始的本次任务轮次；`phase` 是稳定短名称。`done` 代表任务进入终态，成功与否由 evaluate 的实际判据确定。最大时长是超时限制，不是成功判据；未完成轮次不能因达到时长算完成。

`control` 只在每个物理采样时刻调用一次。视觉控制另有相机帧率/延迟时在适配器内调度，保持最近一次观测；记录相机时刻与控制时刻。不要用墙钟决定动作/轮次，墙钟仅做显示节拍。规划状态、随机数生成器均在适配器中显式维护，随机种子取合同。

允许在初始化时恢复姿态；原型记录器拒绝在 control 内直接覆写物理状态。若轮间要求非物理 reset，需扩展框架：完成当前段 → 事件记录 → 新 episode → 复位任务/积分器/执行器 → 新时间轴段；导出时不跨 reset 求导。不允许通过删去状态保护绕过此要求。

## 控制能力与规划

读取原执行器类型和限幅。位置伺服时 ctrl 是目标位置，力矩 motor 时 ctrl 才可能与广义扭矩对应。改变驱动器必须留修改清单、保留能力约束并确认控制方式；gear≠1、腱/耦合驱动不得按一执行器一关节猜测。

默认规划实现应包含：目标位姿生成、受限 IK、碰撞检查、可行路径、速度/加速度约束下的时间参数化、跟踪与接触控制。规划文件记录算法、容差、采样/迭代预算及失败原因。“未找到可行解”与“数学上不可达”分开。

工具/环境/视觉规则可以由适配器更新 mocap 或显示状态，但不得以视觉对象位置替换应有的动态物理物体。外部接触/传感器记录可扩展到 `data/observations/`，在报告登记字段和坐标约定。

## 记录时序

本框架每步顺序为 `mj_forward → control → mj_forward → sample → mj_step`。这样记录的 q、qd、qdd、扭矩、末端状态、接触量都对应同一个瞬时状态。`qdd` 是动力学求解加速度，不是两帧速度的差分。遇到隐式积分、滤波或接触非光滑，积分步后的速度差分不必与瞬时 qdd 完全相等。

本框架不支持 RK4 子步回调控制、自定义积分或并行 GPU 物理；需要这些模式时适配并重新校验，不能用当前记录时序作未经验证的保证。CSV 每步一条/对象，渲染帧率不改变采样间隔。
